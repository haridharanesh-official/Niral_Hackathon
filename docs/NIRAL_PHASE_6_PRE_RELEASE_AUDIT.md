## Security and privacy findings

### New medium-severity finding: HTML injection in invitation email

`apps/api/src/teams/teams.service.ts:241` interpolates stored `team.name` directly into official HTML mail. `dto/team.dto.ts:11–14` permits arbitrary 2–60-character names. A verified enrolled participant who leads a team can supply a name containing an HTML link and invite a target email. Source tracing and an in-memory service/mail mock confirmed the anchor survives into the mail body. No real mail was sent, and no JavaScript execution/account takeover is claimed.

Required remediation: HTML-escape all untrusted text in email templates, add a malicious-markup regression test and review invitation-abuse controls. Role checks authorize sending but do not encode HTML. This audit identifies the issue; it does not claim remediation.

### Residual security gaps, not newly introduced regressions

- `events.gateway.ts:40–42`: private-room chat/typing checks the sender, but previously joined recipients are not revalidated/evicted when membership, session or expiry changes. In-memory room behavior confirmed passive stale recipients can remain. Dashboard push has stronger recipient checks. Baseline was already permissive; retain as a release risk rather than claim this branch introduced it.
- `teams.service.ts:845–857` and `listPublic()`: private-team listing/invite-code/leader-contact exposure and private-visibility joining restrictions remain incomplete. Existing member-email removal improves one surface but does not prove private-team confidentiality. Baseline behavior requires separate remediation review.

Follow [Prisma baselining guidance](https://www.prisma.io/docs/orm/prisma-migrate/workflows/baselining). No production migration, destructive schema action or historical financial-record deletion occurred; test suites clean up only their own synthetic fixture records.
